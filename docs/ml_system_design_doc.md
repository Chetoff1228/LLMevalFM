# **Документ проектирования системы ML: LLMevalFM**

## **Термины и пояснения**

- **LLMevalFM** — фреймворк для оценки фактической точности LLM, который проверяет способность моделей генерировать правдивую информацию в различных контекстах.
- **Фактическая точность (Fact Accuracy)** — способность модели предоставлять верную информацию, соответствующую реальным данным.
- **Большие языковые модели (LLM)** — модели машинного обучения, обученные на больших объемах текстовых данных, предназначенные для генерации, анализа и обработки текста.
- **provac_score**: Числовое значение, указывающее на сложность или важность задачи.
- **Модели** — алгоритмы машинного обучения, предназначенные для выполнения задач генерации текста, обработки информации и ответов на вопросы.

### **1. Обзор системы**

**LLMevalFM** — это фреймворк для оценки фактической точности больших языковых моделей (LLM), предназначенный для анализа способности моделей генерировать правдивую информацию в контексте специфичных данных, включая чувствительные области, такие как политика, экономика и культура.

### **1.1. Цели и задачи**

- **Оценка фактической точности LLM**: Проверка способности LLM давать правильные ответы на вопросы из реального мира.
- **Поддержка чувствительных контекстов**: Включение специфики политических и социокультурных контекстов в оценку моделей.
- **Автоматизация процесса оценки**: Использование автоматизированных инструментов для тестирования и сравнения выводов модели с реальными данными.
- **Метрики для анализа точности**: Внедрение метрик, таких как точность, полнота, F1-score, для всесторонней оценки качества моделей.


#### **1.2 Бизнес-требования**

1. **Универсальность**:  
   Фреймворк должен поддерживать работу с различными LLM, включая модели с кастомизацией под отраслевые задачи (например, медицина, финансы, право). Гибкая архитектура должна предусматривать настройку шаблонов запросов и метрик оценки.
2. **Простота интеграции**:  
   Инструмент должен предоставлять стандартные API (REST/GraphQL), интеграцию через Docker/Kubernetes и возможность локального развертывания для работы в ограниченных сетях. 
3. **Скорость тестирования**:  
   Среднее время обработки 2800 запросов на моделях >70b параметров не должно превышать 60 минут. Для этого требуется параллелизация задач, использование высокопроизводительных вычислительных кластеров и оптимизированные алгоритмы оценки.
4. **Автоматизация**:  
   Минимизация ручного вмешательства за счет автоматической генерации отчетов, классификации ошибок (по категориям: фактологические, логические, контекстуальные) и визуализации результатов. 
5. **Метрики адаптивности**:  
   Фреймворк должен поддерживать базовые метрики (точность, полнота, F1), а также адаптацию под бизнес-задачи (например, оценка юридической точности или медицинской осведомленности).

#### **1.3 Ограничения**

1. **Качество данных**:  
   Достоверность анализа ограничена наличием актуальных эталонных данных. Подключение к обновляемым внешним базам, использование кэширования и периодической проверки данных.
2. **Ресурсы**:  
   Модели с параметрами >70b требуют значительных ресурсов (32+ GB VRAM). Это делает тестирование недоступным для малых компаний. Поддержка квантованных моделей и предоставление малых локальных конфигураций.
3. **Ограничения API**:  
   Зависимость от внешних сервисов накладывает лимиты на частоту запросов, а также на верефицируемость результатов.
4. **Точность метрик**:  
   Метрики вроде "Контекстной осведомленности" могут быть субъективны и сложны в формализации.



#### 2.1 **Входные данные**

- **Текстовые данные**: Запросы и утверждения, которые будут использоваться для оценки фактической точности.
- **Исторические и реальные данные**: Базы данных с проверенной и актуальной информацией, которая будет служить эталоном для сравнения с выводами моделей.

#### 2.2 **Компоненты фреймворка**

- **Модуль тестирования**:
    - Автоматически генерирует запросы для тестирования LLM.
    - Сравнивает ответы модели с фактическими данными из внешних источников (базы данных, API).
    - Обрабатывает текстовые ответы и проводит их анализ на соответствие фактическим данным.

- **Модуль анализа ошибок**:
    - Детектирует и классифицирует типы ошибок.
    - Предоставляет отчёты об ошибках с рекомендациями для улучшения модели.

- **Метрики точности**:
    - Вычисляет точность, полноту, F1-score и другие метрики, которые характеризуют фактическую точность модели.
    - Позволяет проводить сравнительный анализ различных LLM на основе этих метрик.

- **Интерфейс для настройки фреймворка**:
    - Поддержка кастомизации для различных типов запросов и данных.
    - Настройка порогов оценки и выбора метрик.

#### 2.3 **Выходные данные**

- **Отчёты об оценке**:
    - Детализированные отчёты по каждому тесту, показывающие результаты оценки фактической точности модели.
    - Рекомендации для улучшения модели на основе анализа ошибок (по матрица ошибок типов вопросов и сфер, где ошибались модели).

- **Метрики производительности**:
    - **Метрики производительности**: Включают в себя не только точность моделей, но и скорость работы, а также другие важные характеристики, которые позволяют пользователям эффективно сравнивать производительность различных LLM.

#### Подход к тестированию

1. **Генерация запросов**: Система генерирует набор запросов, основанных на реальных данных, которые используются для оценки модели.
2. **Тестирование LLM**: Модель обрабатывает запросы и возвращает ответы.
3. **Сравнение с реальными данными**: Ответы модели сравниваются с фактами из внешних источников данных.
4. **Оценка и анализ**: Результаты сравниваются с заранее установленными метками точности и оценивания.

#### Метрики для оценки

- **Точность (Exact Match)**: Эта метрика показывает, насколько точно ответ модели совпадает с правильным ответом. Она вычисляется как доля случаев, когда модельный ответ идентичен правильному ответу.

  Формула:
  Точность = (Количество совпадений) / (Общее количество вопросов)

- **F1-score (Completeness)**: Оценка того, насколько ответ модели охватывает все важные аспекты вопроса. Полнота может быть вычислена с использованием метрики F1, которая учитывает как точность, так и полноту, что позволяет оценить, насколько хорошо модель отвечает на заданные вопросы.

  Формула:
  F1 = 2 * (Точность * Полнота) / (Точность + Полнота)

- **Контекстная осведомленность (Context Awareness)**: Способность модели давать ответ, соответствующий специфике вопроса и контекста, особенно в тех случаях, когда вопрос может иметь несколько интерпретаций. Эта метрика может быть оценена через коэффициент Левенштейна, который измеряет расстояние между строками.

  Формула:
  Коэффициент Левенштейна = 1 - (d(a, b) / max(|a|, |b|)), где d(a, b) — расстояние Левенштейна между строками a и b.

- **Частичное совпадение (Partial Match)**: Эта метрика оценивает, насколько ответ модели схож с правильным ответом, даже если они не идентичны. Частичное совпадение может быть вычислено с использованием функции вычисления F1, учитывающей частичные совпадения.

  Формула:
  Частичное совпадение = (Количество частичных совпадений) / (Общее количество вопросов)

- **Подстрока (Is Substring)**: Оценивает, содержится ли правильный ответ как подстрока в ответе модели. Это помогает понять, насколько близки ответы модели к правильным, даже если они не идентичны.

  Формула:
  Подстрока = 1, если REAL_ANSWER содержится в MODEL_ANSWER, иначе 0.

#### **2.5. Этапы решения задачи**

#### **Этап 1. Подготовка данных**

#### **Описание данных/сущностей**
Для оценки фактической точности LLM требуется набор данных, который включает разнообразные вопросы с заранее определёнными правильными ответами. В проекте используются данные, которые состоят из различных типов вопросов (открытые, выборы, соответствие и последовательности), и ответы на эти вопросы должны быть точными и соответствовать фактической информации.

**Основные данные включают**:
- **Вопросы**: Включают тему (например, история, география, политика), тип вопроса (открытый ответ, множественный выбор, соответствие), сам вопрос, варианты ответов (если применимо), правильный ответ.
- **Ответы**: Ожидаемый правильный ответ на вопрос. Это может быть текст, числовое значение или набор значений для вопросов множественного выбора.
- **Контекст и провокационность**: Провоцирующие вопросы могут быть использованы для оценки способности модели в нестандартных ситуациях.

**Проблемы с качеством/разметкой**:
- Данные могут содержать размытые или некорректные разметки, особенно для вопросов с множественным выбором или сложными открытыми ответами.
- Не всегда возможно определить точный «правильный» ответ на сложные или субъективные вопросы, что требует дополнительной обработки и анализа.

#### **Процесс генерации данных**
Данные поступают из открытого датасета, состоящего из вопросов и ответов, собранных с различных образовательных и информационных источников. Данные поступают в формате JSON или JSONL, что позволяет легко интегрировать их в систему. Эти данные могут обновляться по мере появления новых источников и обновлений в базе данных.

Данные поступают регулярно, что позволяет обновлять тестовые наборы для актуализации оценок. Однако стоит отметить, что для специфических тем или исторических данных могут потребоваться дополнительные источники или создание новых данных.

#### **Риски и проблемы**
- **Необходимость дополнительных данных**: Для некоторых областей, таких как специализированная политология или экономика, может потребоваться больший объём данных для точной оценки модели.
- **Конфиденциальность данных**: Хотя датасет в основном состоит из публичной информации, могут встречаться элементы, содержащие чувствительные данные, которые требуют очистки или анонимизации.
  
**Способы решения**:
- Для улучшения качества данных может быть полезно применять методы аугментации данных, такие как синтаксические или семантические преобразования, чтобы создать дополнительные примеры на основе имеющихся.
- Для устранения потенциальных рисков с конфиденциальностью необходимо провести анализ данных и скрыть или анонимизировать чувствительные элементы, если такие имеются.

#### **Необходимый результат этапа**
На выходе данного этапа должна быть подготовлена чистая и готовая к использованию таблица с данными, состоящими из вопросов, ответов и мета-информации (например, провокационность, типы вопросов и контексты). Важно также иметь витрину данных, обеспечивающую регулярное обновление и поддержку актуальности данных.

#### **Этап 2. Подготовка прогнозных моделей**

#### **Описание ML-метрик и функций потерь**
Для оценки точности фактических ответов моделей, а также их способности генерировать релевантные ответы, были выбраны следующие метрики:

- **Точность (Exact Match)**: Оценивает процент точных совпадений между предсказанным и правильным ответом.
- **F1-Score**: Важно не только совпадение, но и полнота, с которой модель охватывает все ключевые аспекты вопроса.
- **Коэффициент Левенштейна**: Используется для оценки контекстной осведомленности, показывая, насколько близки ответы модели к правильным.

Для оптимизации работы моделей в задачах оценки фактической точности выбрана комбинация метрик точности и F1-score с дополнительным анализом контекстной осведомленности.

#### **Структура бейзлайна**
Для бейзлайна используется простая модель (например "gpt2"), которая предсказывает наиболее вероятный ответ на основе статистических методов или заранее подготовленных шаблонов. Это позволяет установить базовые метрики для всех последующих более сложных моделей.

#### **Стратегии дальнейшего развития решения**
После установки бейзлайна необходимо будет исследовать более сложные модели, оптимизировать их гиперпараметры, а также улучшать обработку признаков (например, добавление информации о контексте или провокации), промпт инжиниринг, инсрукция добавления шотов.

#### **Анализ и интерпретация работы модели**
- На основе метрик точности и полноты будут анализироваться слабые места в работе модели. В частности, внимание будет уделяться частичным совпадениям и анализу ошибок.
- Для улучшения работы модели можно добавить дополнительные данные для тренировочного набора, что поможет улучшить обоснованность и релевантность ответов.

#### **Риски и способы их снижения**
- **Риски переобучения**: При использовании сложных моделей существует риск переобучения на малых данных. Для снижения этого риска будет использоваться кросс-валидация.
- **Низкое качество ответов для специфичных вопросов**: Для специфичных или сложных вопросов может потребоваться дополнительная настройка модели или добавление тематических данных в обучающий набор.

#### **Необходимый результат этапа**
Результатом этого этапа является создание работающей модели с возможностью оценки точности на тестовых данных, а также с детализированным отчетом по меткам и результатам.

#### **Этап 3. Оценка фактической точности и анализ ошибок**

#### **Описание процесса**
На этом этапе происходит анализ работы обученной модели на заранее подготовленных тестовых данных. Ответы моделей сравниваются с фактическими данными, и определяется точность и полнота их соответствия.

**Этап включает в себя**:
- Сравнение предсказанных ответов с фактическими.
- Оценка метрик точности (Exact Match), F1-score, и анализа контекста.

#### **Риски и способы их снижения**
- **Низкая точность для некоторых типов вопросов**: В таких случаях важно включить дополнительные методы обучения или доработку моделей с учётом специфики вопроса.

#### **Необходимый результат этапа**
На выходе должен быть отчёт с результатами оценки точности модели, выявленными ошибками и рекомендациями для дальнейших улучшений.

#### **Этап 4. Разработка основных компонентов системы**

#### **Этап 4.1 Модуль тестирования**

Модуль тестирования системы LLMevalFM — это компонент, который отвечает за автоматическую генерацию запросов и тестирование моделей. Он должен быть гибким и масштабируемым, чтобы поддерживать разнообразные типы данных и моделей.

**Основные функции модуля тестирования:**
- **Генерация тестовых запросов**: Модуль автоматически генерирует запросы, которые могут быть простыми фактами или более сложными вопросами, учитывая область знаний. Генерация может быть основана на заранее подготовленных шаблонах или на случайных выборках из базы данных.
- **Обработка входных данных**: Модуль должен поддерживать различные форматы данных (например, текст, числовые значения, структуры JSON), а также возможность обработки разнообразных типов вопросов, таких как открытые вопросы, вопросы с множественным выбором или вопросы на соответствие.
- **Тестирование моделей**: Модуль использует подключённые модели для ответа на генерируемые запросы, получает ответы и передаёт их на обработку.
- **Сравнение с эталонными данными**: После получения ответа от модели, модуль тестирования сравнивает его с фактическим ответом, используя заранее подготовленные эталонные данные, такие как базы данных, API или файлы с фактами.

**Риски и способы минимизации**:
- **Малое количество тестов**: Для решения этого риска важно интегрировать функцию генерации случайных тестов на основе заранее подготовленных шаблонов.
- **Некорректные результаты**: Важно использовать контроль качества входных данных и проверку формата запросов, чтобы избежать ошибок при генерации.

---

#### **Этап 4.2 Модуль анализа ошибок**

Модуль анализа ошибок занимается детальным изучением отклонений в работе модели и предоставляет отчёты для дальнейшей оптимизации.

**Основные функции модуля анализа ошибок:**
- **Типы ошибок**: Модуль должен быть в состоянии классифицировать ошибки на несколько типов, например:
  - **Неверный ответ**: Когда модель генерирует неправильную информацию.
  - **Частичное совпадение**: Когда ответ модели частично совпадает с правильным, но не является полностью верным.
  - **Пропущенные элементы**: Когда модель не отвечает на все ключевые части вопроса.
- **Визуализация ошибок**: Для упрощения анализа модуль предоставляет визуализацию ошибок, например, с помощью графиков или таблиц. Это позволяет понять, где модель ошибается чаще всего.
- **Предложения по улучшению**: На основе анализа ошибок, модуль должен предоставлять рекомендации для улучшения модели, такие как добавление данных, изменение алгоритмов или оптимизация гиперпараметров.
**Риски и способы минимизации**:
- **Ошибки в классификации**: Ошибки могут быть вызваны различием в понимании вопросов. Для минимизации риска важно тестировать систему на большем количестве запросов с разнообразными вариантами ответов.
- **Трудности в интерпретации ошибок**: Для решения этой проблемы можно использовать более сложные методы анализа, такие как нейронные сети для классификации ошибок, что позволит более точно выявлять типы ошибок.

---

#### **Этап 5. Интеграция с внешними источниками данных для получения актуальной информации**

#### **Описание и цели интеграции**
Для повышения точности и актуальности оценок фреймворк LLMevalFM должен быть интегрирован с внешними источниками данных, такими как базы данных, API и открытые ресурсы. Это позволит получать актуальную информацию для проверки фактической точности ответов моделей.

**Основные цели интеграции:**
- **Актуализация данных**: Интеграция с внешними источниками, такими как Wikipedia, Google Knowledge Graph, различные открытые API (например, OpenWeather, финансовые данные), для получения актуальных фактов.
- **Автоматизация обновлений**: Система должна автоматически получать обновления из внешних источников для поддержания базы данных фактов актуальной.
- **Обогащение данных**: Внешние данные могут быть использованы для дополнения существующих данных, добавления нового контента или для обработки специфических запросов.

**Риски и способы минимизации**:
- **Задержки в запросах к API**: Для минимизации этих рисков необходимо настроить систему кэширования, которая будет хранить результаты запросов и обновлять их только через заданный интервал времени.
- **Нестабильность API**: Необходимо предусмотреть обработку ошибок и возможность переключения на резервные источники данных в случае недоступности основного API.

---

#### **Этап 6. Разработка интерфейса настройки и создания отчетов**

#### **Описание интерфейса**
Интерфейс настройки и создания отчетов — это важный компонент системы, который позволяет пользователю настраивать параметры тестирования и получать отчёты по результатам работы модели. Он должен быть интуитивно понятным и удобным.

**Основные функции интерфейса:**
- **Настройка параметров тестирования**: Пользователь должен иметь возможность выбрать типы данных для тестирования, настроить пороговые значения для метрик и выбрать модели для сравнения.
- **Создание отчётов**: Интерфейс должен автоматически генерировать отчёты по результатам работы модели, включая подробную информацию о метриках, ошибках, а также предложения по улучшению.
- **Экспорт данных**: Возможность экспортировать отчёты в различные форматы, такие как PDF, Excel или JSON для дальнейшего анализа.

**Риски и способы минимизации**:
- **Низкая гибкость интерфейса**: Важно проектировать интерфейс с учётом будущих расширений, добавляя поддержку новых моделей и метрик.
- **Проблемы с совместимостью форматов отчётов**: Для решения этих проблем можно предусмотреть поддержку нескольких форматов для экспорта данных и использовать библиотеки для генерации отчетов, такие как `ReportLab` для PDF.

---

#### **Этап 7. Тестирование фреймворка с реальными данными и моделями**

#### **Процесс тестирования**
Тестирование фреймворка — это этап, на котором проверяется, насколько эффективно работают все компоненты системы на реальных данных и моделях. Этот этап включает в себя несколько ключевых процессов:

- **Системное тестирование**: Проверка всех компонентов системы на корректную работу. Включает в себя проверку взаимодействия всех модулей.
- **Модульное тестирование**: Тестирование каждого компонента системы в отдельности.
- **Тестирование моделей**: Оценка точности и качества работы моделей с реальными данными. Применяются метрики, такие как точность, F1-score, и анализ ошибок.

**Риски и способы минимизации**:
- **Низкая точность модели на реальных данных**: Для минимизации этого риска необходимо использовать больший объём данных для тестирования и разработать стратегию обработки нестандартных или нестабильных данных.

#### **Этап 8. Оптимизация и улучшение системы на основе результатов тестирования**

#### **Цели и задачи оптимизации**
После проведения тестов необходимо выполнить анализ полученных данных и оптимизировать систему для повышения её производительности и точности.

**Основные задачи оптимизации:**
- **Оптимизация гиперпараметров моделей**: Применение методов поиска гиперпараметров, таких как случайный поиск или байесовская оптимизация, для нахождения наилучших параметров моделей.
- **Улучшение качества данных**: Если результаты тестирования показали слабые места в данных, необходимо их дополнить или улучшить. Это может включать в себя добавление новых данных, улучшение разметки или использование других источников данных.
- **Параллельная обработка**: Для повышения производительности можно внедрить параллельную обработку, особенно при работе с большими объёмами данных и моделями.

**Риски и способы минимизации**:
- **Проблемы с переобучением**: Для этого важно использовать методы регуляризации и кросс-валидации.
- **Недостаточная производительность системы**: В случае проблем с производительностью может потребоваться использование более эффективных методов обработки данных или улучшение инфраструктуры.

### Этап 3. Подготовка пилота

#### **3.1. Способ оценки пилота**

Пилотный этап будет оцениваться по следующему подходу:

1. **Дизайн эксперимента**:
   - Тестирование LLM проводится на наборе данных SLAVA, который представляет собой широкий спектр социально-политических вопросов, сложных и провокационных.
   - Для каждого вопроса модель генерирует ответ, который затем сравнивается с эталонными данными или проверяется экспертами.
   - Результаты оцениваются с использованием автоматизированных метрик точности и полноты, а также экспертной оценки, если требуется.

2. **Роли участников**:
   - **Product Owner**: Проверяет соответствие результатов требованиям бизнеса, следит за достижением ключевых метрик.
   - **Data Scientist**: Анализирует данные, проводит оценку моделей и настраивает фреймворк.
   - **AB Group**: Обеспечивает контроль качества и реализацию эксперимента на контрольных и экспериментальных группах данных.

3. **Ключевые этапы оценки**:
   - Подготовка и загрузка тестового набора данных.
   - Проведение серии тестов на выбранных LLM.
   - Сравнение результатов модели с эталонными данными.
   - Генерация отчетов, включающих анализ ошибок и рекомендации по улучшению модели.

---

#### **3.2. Что считаем успешным пилотом**

**Успешный пилот** определяется достижением следующих целей:

1. **Формализованные метрики успеха**:
   - **Factual Accuracy (Точность фактической информации)**: Доля корректных ответов, предоставленных моделью.
   - **Recall (Полнота)**: Способность модели охватить как можно больше правильной информации по заданному запросу.
   - **F1-score**: Баланс между точностью и полнотой, обеспечивающий общую оценку производительности.
   - **Provocative Question Handling (Устойчивость к провокационным вопросам)**: Процент корректных ответов на сложные или чувствительные запросы.
   - **Response Time (Скорость ответа)**: Среднее время генерации ответа моделью.

2. **Удовлетворение ожиданий Product Owner**:
   - Модель демонстрирует высокий уровень точности (например, F1-score ≥ 0.85) в ключевых категориях вопросов.
   - Устойчивость к ошибкам и соответствие ожиданиям по провокационным вопросам.

3. **Успешное внедрение**:
   - Фреймворк настроен и протестирован, готов к использованию на реальных данных.
   - Обратная связь от Product Owner и экспертов свидетельствует о практической применимости пилота.

---

#### **3.3. Подготовка пилота**

#### **Ожидаемые затраты на вычисления**
- **Оценка вычислительных ресурсов**:
   - **Базовый эксперимент**: Выполняется с использованием моделей средней вычислительной сложности (например, моделей с параметрами до 6B).
   - **Анализ времени и мощности**: Рассчитывается количество запросов, время обработки на каждую модель и общий объем вычислительных мощностей.
   - **Этап уточнений**: Если вычислительная сложность превышает доступные ресурсы, пилот адаптируется путём снижения объёма тестовых данных или перехода на модели меньшего размера.

#### **Установленные ограничения**:
- Время выполнения полного тестирования не должно превышать 48 часов на базовых вычислительных мощностях.
- Использование моделей с ограничением памяти (например, 32GB GPU).

#### **Процесс уточнения параметров пилота**:
1. **Эксперимент с бейзлайном**:
   - Выбирается базовая модель (например, GPT-3.5).
   - Проводится тестирование на ограниченном наборе данных (10% от SLAVA) для оценки времени и точности.
   - На основе результатов уточняются параметры тестов (количество вопросов, модель, дополнительные ресурсы).

2. **Уточнение ограничений**:
   - Устанавливаются ограничения на вычислительную сложность моделей.
   - Формируется конечный план, включающий оптимальные модели и количество тестовых запросов.

3. **Финализация**:
   - Подготовленный пилот согласовывается с Product Owner.
   - Внедряются изменения, направленные на снижение вычислительных затрат и увеличение эффективности.


### Этап 4. Внедрение

#### **4.1 Архитектура решения**
- **Блок-схема**: Архитектура решения представляет собой несколько ключевых сервисов, каждый из которых выполняет свою роль в процессе обработки запросов и предоставления ответов.
  - **ICI Bot** — чатбот для обработки запросов от пользователей.
  - **TG-бот (@AgoraLLM_bot)** — интерфейс для общения с пользователями через Telegram.
  - **SLAVA Leaderboard** — система для оценки моделей на основе их производительности, доступная через Hugging Face.
  - **MongoDB** — хранилище данных, используемое для сохранения запросов, ответов и результатов.
  - **Streamlit Interface** — интерфейс для визуализации данных и статистики.

  **Картинка архитектуры решения**:
  ![Architecture_Schema](https://github.com/Chetoff1228/LLMevalFM/blob/hw_4/extensions/framework.png)

#### **4.2 Описание инфраструктуры и масштабируемости**
- **Выбор инфраструктуры**: Для развертывания и масштабирования системы используются контейнеры Docker для изоляции сервисов и их управления. 
  - MongoDB используется для хранения данных, так как она обеспечивает гибкость и масштабируемость.
  - Веб-интерфейс (Streamlit) предоставляется через Docker контейнеры.
- **Плюсы**:
  - **Docker**: позволяет легко масштабировать систему и управлять зависимостями.
  - **MongoDB**: оптимален для работы с большими объемами данных и масштабируемостью.
  - **Streamlit**: простой в использовании для создания веб-интерфейса.
- **Минусы**:
  - Для масштабирования на более высокие нагрузки потребуется дополнительная настройка контейнеров.
- **Почему выбран этот вариант**: Этот выбор является оптимальным для текущих требований по гибкости, скорости развертывания и масштабируемости.

#### **4.3 Требования к работе системы**
- **SLA**: Система должна обеспечивать время отклика на запросы не более 3 секунд на инференс при условии стандартной нагрузки.
- **Пропускная способность**: Система должна поддерживать одновременные запросы от не менее 10 пользователей, с возможностью масштабирования по мере необходимости.
- **Задержка**: Время отклика может варьироваться в зависимости от сложности запроса, однако на лидерборде отклик моментальный.

#### **4.4 Безопасность системы**
- **Потенциальные уязвимости**:
  - Уязвимость в API-интерфейсах: необходима защита от DDoS-атак и несанкционированного доступа.
  - Потенциальная угроза утечек данных: необходимо использовать безопасные протоколы и шифрование для передачи данных.
  
#### **4.5 Безопасность данных**
- **GDPR и другие законы**: Для обеспечения соответствия законам, таким как GDPR, необходимо исключить сбор и обработку личных данных без согласия пользователей. Система должна хранить только анонимизированные данные о запросах и ответах.
- **Политика безопасности данных**: Все данные, включая историю запросов, должны быть защищены через шифрование и должны быть доступными только для уполномоченных пользователей.

#### **4.6 Integration points**
- **API взаимодействия**:
  - Интеграция с Telegram API для отправки и получения сообщений через бот.
  - API для взаимодействия с Leaderboard на Hugging Face, чтобы предоставить пользователям доступ к результатам.
  - Интерфейс с MongoDB для сохранения запросов и их результатов.

#### **4.7 Риски**
- **Риски**:
  - **Высокая нагрузка**: При увеличении числа пользователей, система может столкнуться с ухудшением производительности, если не будет обеспечена дополнительная масштабируемость.
  - **Неопределенность в точности LLM**: Поскольку модели используют большие объемы данных, возможны погрешности в результатах.
  - **Проблемы с безопасностью данных**: При неправильной настройке системы защиты могут быть угрозы утечек данных.
